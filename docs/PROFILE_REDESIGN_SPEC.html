My Profile redesign: sticky summary, scrollable form panels

A cleaner layout for profile.php. The profile summary card stays visible while the page scrolls. The Edit profile and Change password forms become separate panels whose content scrolls on its own while each panel's heading and Save button stay in place. On phones and short screens the page falls back to a plain stacked layout.

Draft for implementation No migration No new dependencies One small POST change

01Scope and requirements

Every change stays inside the existing root-page pattern: profile.php keeps its own POST handling, SQL and markup. Nothing moves into app/. The work touches four files: profile.php, assets/styles.css, assets/app.js, and nothing else. No schema change, no library and no build step. Verification is php -l profile.php and node --check assets/app.js, followed by the manual test plan in section 12.

The brief refers to a “Change Profile” section. The page has no section with that name. The second form on the page is Change password, and this spec reads the requirement as referring to it.

02Current page

What the code does today, and the details the new layout must work with:

  • Structure. .profile-layout is a two-column grid (minmax(0,320px) minmax(0,1fr), align-items:start). On the left is section.card.profile-summary: avatar, name, title, six label/value rows and the permission tags. On the right, .profile-forms stacks two form.card.form elements. The columns stack at a viewport width of 999px or less (styles.css ≈ line 1069).
  • Top bar. .util-bar is position:sticky; top:0; z-index:1000. It is transparent with pointer-events:none, but its 44px buttons still cover roughly the top 76px of the viewport on desktop. Anything that sticks has to sit below it.
  • Entry animation. Each child of .content.fade-in runs fadeInUp with animation-fill-mode: both on transform. Because the animation stays in effect, browsers can treat that ancestor as a stacking context and as the containing block for position:fixed descendants. See D1.
  • Page scrolling. body{overflow-x:hidden} passes through to the viewport because html sets no overflow, so the viewport stays the scroll container and position:sticky works. Keep it that way: an overflow value other than visible on .app-shell, .app-main or .content would silently break every sticky element in the app. Use overflow-x:clip if clipping is ever needed.
  • Accessibility gaps. The Full name, Email, Job title and all three password fields have <label> elements without a for/id pairing, so screen readers don't announce their labels. Only the photo input is paired correctly.
  • Theme override. light-theme-v3.css loads last and styles html[data-theme="light"] .card (specificity 0,2,1). New panel rules must leave card surface colors to that file and scope their layout rules as .profile-page .profile-panel.
  • Existing pattern to reuse. The candidate profile's .cprofile-snapshot already uses sticky with a @supports not (position:sticky) fallback and turns sticky off at 767px and below. It also uses @container page queries on .page-container, so its layout responds to the sidebar collapsing, not just to the viewport width. This spec follows the same approach.

03Design decisions

D1 · Use position: sticky, not position: fixed

A fixed card is taken out of the grid. That means it needs a placeholder and JavaScript to keep its width in step with the column every time the sidebar opens or collapses. It would also be positioned against the fade-in ancestor rather than the viewport (see §2), so it could drift with the content. A sticky card stays in its grid column, keeps its width with no script, and stops at the bottom edge of .profile-layout, so it can never overlap the footer.

D2 · Only the panel body scrolls. The heading and Save button stay put.

Each form panel is a three-part flex column: a heading, a body and a footer. Only the body scrolls. The Save button is always on screen, and because the heading and footer sit outside the scrolling area, a focused field can never end up hidden underneath them (WCAG 2.4.11). A sticky heading inside the scrolling area would need scroll-padding tuning to avoid exactly that problem.

D3 · Panels cap at the viewport height and scroll only when they overflow

A panel's maximum height is the space below the top bar. The body uses overflow-y:auto, so a scrollbar appears only when the content is taller than that. On a 900px-tall screen, Change password fits and doesn't scroll at all. On a 720px laptop, Edit profile scrolls. Forcing a fixed-height scroll area onto a three-field form would add a scrollbar with no purpose. On phones, and on screens under 560px tall, the cap is removed entirely (§9).

D4 · Let scrolling continue from a panel to the page

overscroll-behavior-y is deliberately left at auto. Once a panel reaches its end, further mouse-wheel or trackpad scrolling moves the page. contain is right for modals, but here it would trap people scrolling down the right-hand column, and that stuck feeling is what this redesign is meant to remove.

D5 · No polyfills

Every feature used is supported at the browser floor in §11. Sticky has an @supports fallback to static positioning. The JavaScript is an optional enhancement: without it the page keeps the sticky card and scrolling panels but loses the edge shadows, the “stuck” elevation and the fit guard. Old sticky polyfills such as Stickyfill are unmaintained and aren't needed.

04Target layout

Desktop, shown when the page container is at least 820px wide and the viewport is at least 560px tall. The container width is what counts, which is about a 1280px window with the sidebar open. Collapsing the sidebar can switch a smaller window into this layout.

Visual hierarchy changes (R1)

  • Identity block first. Avatar, name and job title, followed by role and account status as two pills instead of two label/value rows. Those two facts are what someone checks at a glance.
  • Facts as a description list. Email, Member since, Password changed and Seats become a <dl> with hairline dividers, labels in muted text and values in semibold. Long emails wrap instead of pushing the column wider.
  • Collapsible permissions. “What your account can do” becomes a <details> with a count pill. It starts open when there are four permissions or fewer and closed when there are more. This is also the main way the sticky card is kept short enough to fit (R5).
  • Jump links. Two small secondary buttons at the bottom of the card, Edit profile and Change password, link to the two panels. These are ordinary anchors, so they work without JavaScript (R4).
  • Panel headings with a one-line description of what each form changes, and a footer bar that keeps the button right-aligned. On phones the button is full width, as it is today.
  • Save messages in the panel. The success or error message after saving appears inside the panel that was submitted, not above the page (§5.3).

07JavaScript: app.js

Add a new self-contained function block after the dropzone block, in the same style as the other modules in app.js. It does nothing on pages without [data-profile-page]. It uses IntersectionObserver for the scroll edges and the “stuck” state, so no layout is read on every scroll event, and ResizeObserver to keep the top offset and fit guard current.

assets/app.jsappend
/* ==========================================================================
   My profile — sticky summary guard, stuck state, panel scroll edges
   Enhancement only: without it the CSS layout still works; this adds the
   edge shadows, the stuck elevation and the too-tall guard.
   ========================================================================== */
(function () {
  const page = document.querySelector('[data-profile-page]');
  if (!page) return;
  const root = document.documentElement;
  const bar = document.querySelector('[data-util-bar]');
  const summary = page.querySelector('[data-profile-summary]');
  const sentinel = page.querySelector('[data-stick-sentinel]');
  const canObserve = 'IntersectionObserver' in window;

  // The sticky offset and the page's scroll padding follow the util bar's
  // real height, which differs between breakpoints.
  function syncBar() {
    const h = bar ? bar.offsetHeight : 0;
    root.style.setProperty('--util-bar-h', h + 'px');
    root.style.scrollPaddingTop = (h + 12) + 'px';   // focused fields never land under the bar
  }

  // A sticky card taller than the space under the bar would hide its own
  // lower half until the page ends — so it only sticks when it fits.
  function fitSummary() {
    if (!summary) return;
    summary.classList.remove('is-too-tall');
    const cs = getComputedStyle(summary);
    if (cs.position !== 'sticky') return;
    const room = window.innerHeight - (parseFloat(cs.top) || 0) - 16;
    summary.classList.toggle('is-too-tall', summary.offsetHeight > room);
  }

  // Stuck state: once the sentinel above the layout passes the sticky line,
  // the card is pinned and gets a raised shadow.
  let stuckObserver = null;
  function watchStuck() {
    if (!summary || !sentinel || !canObserve) return;
    if (stuckObserver) stuckObserver.disconnect();
    const top = parseFloat(getComputedStyle(summary).top) || 0;
    stuckObserver = new IntersectionObserver(function (entries) {
      const e = entries[0];
      const sticky = getComputedStyle(summary).position === 'sticky';
      summary.toggleAttribute('data-stuck', sticky && !e.isIntersecting && e.boundingClientRect.top < top);
    }, { rootMargin: (-Math.ceil(top)) + 'px 0px 0px 0px' });
    stuckObserver.observe(sentinel);
  }

  // Scroll edges: a 1px marker at each end of a panel body. A marker out of
  // view means more content that way, so show that edge's shadow. When both
  // are in view nothing scrolls, and the body leaves the tab order.
  if (canObserve) {
    page.querySelectorAll('[data-profile-panel]').forEach(function (panel) {
      const body = panel.querySelector('[data-panel-body]');
      const edges = body ? body.querySelectorAll('[data-edge]') : [];
      if (edges.length !== 2) return;
      const seen = { top: true, bottom: true };
      const io = new IntersectionObserver(function (entries) {
        entries.forEach(function (e) { seen[e.target.dataset.edge] = e.isIntersecting; });
        panel.toggleAttribute('data-more-above', !seen.top);
        panel.toggleAttribute('data-more-below', !seen.bottom);
        if (seen.top && seen.bottom) body.removeAttribute('tabindex');
        else body.setAttribute('tabindex', '0');
      }, { root: body });
      edges.forEach(function (el) { io.observe(el); });
    });
  }

  // One batched refresh per frame for resizes, bar changes and <details> toggles.
  let queued = false;
  function refresh() {
    if (queued) return;
    queued = true;
    requestAnimationFrame(function () { queued = false; syncBar(); fitSummary(); watchStuck(); });
  }
  refresh();
  window.addEventListener('resize', refresh);
  if ('ResizeObserver' in window) {
    const ro = new ResizeObserver(refresh);
    if (bar) ro.observe(bar);
    if (summary) ro.observe(summary);
  }

  // After a save, the redirect lands on the submitted panel (#pf-edit or
  // #pf-password). Move focus to its message so screen readers announce it.
  const note = page.querySelector('.profile-panel .notice');
  if (note) { note.tabIndex = -1; note.focus({ preventScroll: true }); }
})();

Why this can't loop: fitSummary() only switches position, which doesn't change the card's size, so the ResizeObserver never fires again because of it. syncBar() sets a custom property the bar itself doesn't use.

08Layering and z-index

The sticky card gets z-index:1 and nothing higher. It never overlaps other page content: it sits in its own grid column and stops at the bottom of the layout. The z-index only keeps its shadow above the neighboring column. It also sits inside the .fade-in stacking context, so no value it could be given would lift it above the app's global layers. That is intentional.

Why no scrolling inside panels on touch screens. A scroll area inside a scrolling page is easy to get stuck in with a thumb, and on iOS the collapsing address bar changes the viewport height mid-gesture. On phones, the jump links and the normal page scroll cover the “don't lose context” goal. The candidate profile already turns off its sticky strip at 767px and below for the same reason.

100dvh (with a 100vh fallback declared first) means that on iPad Safari, where the desktop layout can apply, the panel cap follows the visible viewport as the toolbar shows and hides, instead of extending underneath it.

10Accessibility

Target: WCAG 2.2 AA. The requirements specific to this change:

  • Labels (1.3.1, 4.1.2). Every input has a for/id pair and hints are linked with aria-describedby (§5.2). This fixes an existing bug. autocomplete tokens are added for name, email, organization title, username and passwords (1.3.5).
  • Keyboard access to scrolling areas (2.1.1). Tabbing into a field scrolls it into view inside its panel, and the panel scrolls when the page doesn't. A panel body that actually overflows also gets tabindex="0", so someone reading non-focusable text such as hints can focus the area and scroll it with the arrow keys, Page Up/Down and Space. When nothing overflows, the tabindex is removed so there is no pointless extra tab stop. This passes axe's scrollable-region-focusable rule in both states.
  • Names for scrolling areas. Each body is role="group", labelled by its panel heading, so focusing it announces “Edit profile, group” rather than an unnamed element. The form itself is labelled by the same heading, so the two forms show up as distinct form landmarks.
  • Focus not hidden (2.4.11). The heading and footer sit outside the scrolling body, so they can't cover a focused field. scroll-padding-top on html is set from the bar's measured height, so fields reached by tabbing through the page don't stop under the top bar's buttons.
  • Visible focus (2.4.7). The app's global :focus-visible ring (2px outline, 2px offset) needs 4px outside every control. The body's side padding (22px) and top/bottom padding (8px/12px) leave room, so rings are never clipped by overflow. A focused scrolling body draws its ring inset (outline-offset:-2px) for the same reason.
  • Save messages. After a save, the message appears inside the submitted panel with role="status" (or alert for errors) and is given focus, so it is announced without searching the page.
  • Jump links are ordinary anchors. Following one moves the browser's sequential-focus starting point to the panel, so the next Tab goes to the first field inside it. No script is needed for that.
  • Reflow (1.4.10). At 320 CSS px (1280px at 400% zoom) the page is the single stacked column with no horizontal scroll and no inner scrolling.
  • Motion (2.3.3). Shadow transitions and smooth anchor scrolling are turned off under prefers-reduced-motion: reduce.

13Acceptance criteria

  • T1–T16 pass in every supported browser, with each role run at least once in Chrome and once in Safari.
  • On desktop the summary card stays pinned below the top bar, never overlaps other content, and switches to static when it doesn't fit.
  • Edit profile and Change password each scroll on their own only when their content overflows, with their headings and Save buttons always visible.
  • Edge shadows appear only when there is more content in that direction.
  • On phones and short screens: one column, nothing sticky, no scrolling inside panels.
  • Every input has a programmatic label; keyboard focus is visible and unobscured throughout.
  • php -l profile.php and node --check assets/app.js pass; no new files, dependencies or migrations.
  • Saving each form still writes exactly the same data and audit entries as before. Only the redirect target and where the message appears have changed.

14Out of scope and risks

  • Out of scope: a password strength meter, a warning about unsaved changes, keeping entered values after a failed save (the page reloads after every POST, as it does today), and any change to app/Controllers/AuthController.
  • Risk: scrolling inside the page on desktop. Some people find a second scrolling area inside the page confusing. Decisions D3 and D4 keep it to cases where content actually overflows and never trap the wheel. If testing still shows friction, the fallback is to remove the panel cap (one line in the container query) and keep the sticky card and jump links, which still meet R2 and R4.
  • Risk: new ancestor overflow. Any later overflow:hidden on .app-main or .content will switch off sticky here and everywhere else the app uses it (sidebar, candidate snapshot, scorecard, interview schedule). Worth a comment next to body{overflow-x:hidden}.
